## 1. Лабораторийн зорилго

Энэхүү лабораторийн ажлын зорилго нь Mockito framework ашиглан Java application-ийн unit test боловсруулах, тухайн тестлэгдэж буй классын гаднын хамаарлуудыг mock object-оор орлуулах, мөн method-ийн үр дүн болон объектуудын хоорондын харилцан үйлчлэлийг шалгахад оршино.

Лабораторийн хүрээнд `CourseRegistrationService` классыг тестийн үндсэн объект болгон сонгосон. Тус класс нь оюутны хичээлд бүртгүүлэх үйл ажиллагааг удирдах бөгөөд дараах хоёр үндсэн хамааралтай:

- **`StudentRepository`** — оюутны мэдээлэл хайх, хичээл байгаа эсэхийг шалгах, урьдчилсан нөхцөл авах болон бүртгэлийг хадгалах үүрэгтэй.
- **`EmailSender`** — бүртгэл амжилттай болсон үед оюутанд баталгаажуулах имэйл илгээх үүрэгтэй.

Эдгээр хамаарлыг бодит database эсвэл имэйл үйлчилгээтэй холбохгүйгээр Mockito-ийн mock object ашиглан орлуулсан. Ингэснээр `CourseRegistrationService` классын бизнес логикийг бусад системийн бүрэлдэхүүн хэсгээс тусгаарлан шалгах боломж бүрдсэн.

Лабораторийн ажлын гол зорилтууд:

1. Mockito ашиглан mock object үүсгэх.
2. `when()` болон `thenReturn()` ашиглан mock method-ийн хариу үйлдлийг тодорхойлох.
3. `verify()` болон `never()` ашиглан method-ийн дуудалт, харилцан үйлчлэлийг шалгах.
4. `ArgumentCaptor` ашиглан method-д дамжуулсан аргументыг шалгах.
5. JUnit 5-ийн parameterized test ашиглан олон нөхцөлийг нэг тестийн загвараар шалгах.
6. Mutation testing ашиглан тестүүд бодит кодын алдааг илрүүлэх чадвартай эсэхийг турших.

## 4. Лабораторийн ажлын хэрэгжилтийн явц

Энэ лабораторийн ажлыг зөвхөн тест бичихээс гадна тестийн орчныг бэлтгэх, хамаарлуудыг тусгаарлах, өөр өөр нөхцөлүүдийг шалгах, үр дүнг баталгаажуулах болон тестийн найдвартай байдлыг турших дарааллаар гүйцэтгэсэн.

### 4.1. Төслийн орчин бэлтгэх

Эхний алхамд Maven төслийн бүтцийг бэлтгэж, `pom.xml` файлд JUnit Jupiter болон Mockito dependency-үүдийг тохируулсан.

JUnit 5 нь тестийн үндсэн framework-ийн үүрэг гүйцэтгэж, Mockito нь тестлэгдэж буй классын гаднын хамаарлуудыг орлуулах боломж олгосон.

Тестийн класст дараах annotation-уудыг ашигласан:

- `@ExtendWith(MockitoExtension.class)` — Mockito-г JUnit 5-ийн тестийн орчинтой холбох.
- `@Mock` — mock объект үүсгэх.
- `@InjectMocks` — mock хамаарлуудыг тестлэгдэж буй service объектод автоматаар дамжуулах.

Ингэснээр repository болон email sender-ийн бодит хэрэгжилтийг ажиллуулах шаардлагагүй болсон.

### 4.2. Mock object болон test case бэлтгэх

Дараагийн алхамд `StudentRepository` болон `EmailSender` объектуудыг mock болгон тодорхойлсон.

Mockito-ийн `when().thenReturn()` бүтцийг ашиглан тодорхой method дуудагдах үед ямар утга буцаахыг урьдчилан тохируулсан.

Жишээлбэл:

```java
when(repository.findStudent("S001"))
    .thenReturn(student);
```

Энэ тохиргоогоор `findStudent("S001")` дуудагдах үед бодит database руу хандахгүйгээр бэлтгэсэн `student` объектыг буцаана.

Үүний дараа тест бүрийг Arrange–Act–Assert (AAA) зарчмаар зохион байгуулсан:

1. **Arrange** — шаардлагатай mock тохиргоо болон тестийн өгөгдлийг бэлтгэх.
2. **Act** — шалгах method-ийг ажиллуулах.
3. **Assert** — буцаасан үр дүн болон хүлээгдэж буй нөхцөлийг шалгах.

### 4.3. A1–A7: Үндсэн unit test-үүд

Эхний долоон тестээр бүртгэлийн үйл ажиллагааны амжилттай болон алдаатай нөхцөлүүдийг тус тусад нь шалгасан.

| Тест | Шалгах нөхцөл | Хүлээгдэж буй үр дүн |
|---|---|---|
| A1 | Идэвхтэй оюутан шаардлагатай хичээлд амжилттай бүртгүүлэх | `OK`, бүртгэл хадгалагдаж имэйл илгээгдэнэ |
| A2 | Оюутны мэдээлэл олдохгүй байх | `ERROR_NO_STUDENT` |
| A3 | Оюутан идэвхгүй байх | `ERROR_INACTIVE_STUDENT` |
| A4 | Хичээлийн урьдчилсан нөхцөл хангагдаагүй байх | `ERROR_PREREQUISITES` |
| A5 | Бүртгэлийн дараа имэйл илгээхэд exception гарах | Бүртгэл `OK` хэвээр үргэлжилнэ |
| A6 | `studentId` эсвэл `courseId` null байх | `IllegalArgumentException` шидэгдэнэ |
| A7 | Илгээх имэйлийн агуулга зөв эсэх | `ArgumentCaptor` ашиглан аргументыг шалгана |

**A1 — Амжилттай бүртгэл**

Оюутан идэвхтэй бөгөөд сонгосон хичээлийн урьдчилсан нөхцөлүүдийг хангасан үед service `OK` буцаах ёстой. Үүнээс гадна `saveRegistration()` болон `EmailSender.send()` method-ууд дуудагдсан эсэхийг `verify()` ашиглан шалгасан.

**A2 — Оюутан олдохгүй байх**

Repository-оос `null` буцаах нөхцөлийг тохируулж, service `ERROR_NO_STUDENT` буцааж байгааг шалгасан. Энэ үед бүртгэл хадгалах болон имэйл илгээх үйлдэл хийгдэх ёсгүй. Үүнийг `never()` ашиглан баталгаажуулсан.

**A3 — Идэвхгүй оюутан**

Оюутны `active` төлөв `false` байх үед бүртгэлийг үргэлжлүүлэхгүй, `ERROR_INACTIVE_STUDENT` буцаах ёстой. Мөн имэйл илгээгдэхгүй болон бүртгэл хадгалагдахгүй байхыг шалгасан.

**A4 — Урьдчилсан нөхцөл хангагдаагүй байх**

Оюутны өмнө судалсан хичээлүүд болон сонгосон хичээлийн prerequisite мэдээллийг харьцуулж, шаардлагатай хичээл дутуу үед `ERROR_PREREQUISITES` буцааж байгааг шалгасан.

**A5 — Имэйл илгээх үеийн exception**

Бүртгэл амжилттай хадгалагдсаны дараа `EmailSender` runtime exception шидэх нөхцөлийг үүсгэсэн. Имэйл илгээх ажиллагааны алдаа нь бүртгэлийн үндсэн үйл ажиллагааг буцааж хүчингүй болгох ёсгүй тул service `OK` буцааж байгааг шалгасан.

**A6 — Null оролтын шалгалт**

`studentId` эсвэл `courseId` null үед `IllegalArgumentException` шидэгдэх ёстой. Мөн эдгээр буруу оролтын үед repository болон email sender-тэй харилцахгүй байгааг шалгасан.

**A7 — ArgumentCaptor**

Энэ тестээр зөвхөн method дуудагдсан эсэхийг шалгахаас гадна `EmailSender.send()` method-д дамжуулсан аргументын бодит утгыг шалгасан.

Хүлээгдэж буй имэйлийн body:

```text
CS313 хичээлд амжилттай бүртгэгдлээ.
```

`ArgumentCaptor` ашигласнаар mock method руу дамжуулсан мэдээлэл зөв эсэхийг баталгаажуулах боломжтой болсон.

### 4.4. A8: Parameterized test

A1–A7 тестүүд тус тусдаа тодорхой нөхцөл шалгаж байсан бол A8 тестээр JUnit 5-ийн `@ParameterizedTest` болон `@CsvSource` ашиглан хэд хэдэн алдаатай нөхцөлийг нэг тестийн method-оор шалгасан.

A8-ийн хүрээнд дараах гурван нөхцөлийг туршсан:

1. Оюутны мэдээлэл олдохгүй байх.
2. Сонгосон хичээл системд байхгүй байх.
3. Хичээлийн урьдчилсан нөхцөл хангагдаагүй байх.

Нөхцөл бүрт тохирох өгөгдлийг `@CsvSource` ашиглан дамжуулж, хүлээгдэж буй алдааны кодтой харьцуулсан.

Ингэснээр ижил төстэй тестийн логикийг давтан бичих шаардлага багасаж, тестийн код илүү цэгцтэй болсон.

Мөн parameterized test-д ашигласан нийтлэг mock тохиргооны зарим нь тодорхой нөхцөлд дуудагдахгүй байж болох тул шаардлагатай stubbing-д `lenient()` тохиргоо ашигласан. Энэ нь тухайн тестийн хувилбарт ашиглагдаагүй stub-ээс үүдэх unnecessary stubbing алдаанаас сэргийлсэн.

### 4.5. Бүртгэлийн үйл ажиллагааны дараалал

`CourseRegistrationService.register()` method нь бүртгэлийн хүсэлтийг тодорхой дарааллаар шалгаж, шаардлагатай нөхцөлүүд хангагдсан үед бүртгэлийг хадгалдаг.

Үйл ажиллагааны дараалал:

1. **Оролтын шалгалт:** `studentId` болон `courseId` null эсэхийг шалгана. Аль нэг нь null бол `IllegalArgumentException` шиднэ.
2. **Оюутан хайх:** `StudentRepository.findStudent()` ашиглан оюутны мэдээллийг авна. Олдохгүй бол `ERROR_NO_STUDENT` буцаана.
3. **Идэвхтэй төлөв шалгах:** Оюутан идэвхгүй бол `ERROR_INACTIVE_STUDENT` буцаана.
4. **Хичээл шалгах:** Сонгосон хичээл системд байхгүй бол `ERROR_NO_COURSE` буцаана.
5. **Урьдчилсан нөхцөл шалгах:** Оюутны өмнө судалсан хичээлүүдийг тухайн хичээлийн prerequisite жагсаалттай харьцуулна. Шаардлагатай хичээл дутуу бол `ERROR_PREREQUISITES` буцаана.
6. **Бүртгэл хадгалах:** Бүх шалгалт амжилттай бол `saveRegistration()` method-ийг дуудна.
7. **Имэйл илгээх:** Бүртгэл хадгалсны дараа баталгаажуулах имэйл илгээнэ. Имэйл илгээх үед `RuntimeException` гарсан ч бүртгэлийн үр дүнг буцааж хүчингүй болгохгүй.
8. **Амжилттай дуусах:** Үйл ажиллагаа `OK` үр дүнгээр дуусна.

Энэхүү дараалал нь тестүүдийн хамрах нөхцөлүүдийг ойлгоход тусална. Мөн эрт буцаах (`early return`) логикийн ачаар нэг нөхцөл хангагдаагүй үед дараагийн үйлдлүүд шаардлагагүйгээр хийгдэхгүй.

## 5. Mutation Testing

Unit test-үүд амжилттай ажиллах нь дангаараа тухайн тестүүд кодын алдааг илрүүлэх чадвартай гэдгийг бүрэн батлахгүй. Иймээс тестийн чанарыг нэмэлтээр шалгахын тулд mutation testing хийсэн.

Mutation testing-ийн үед үндсэн source code-д зориудаар жижиг өөрчлөлт оруулж, өмнө нь амжилттай ажиллаж байсан тестүүд тухайн өөрчлөлтийг илрүүлж чадаж байгаа эсэхийг шалгасан.

Энэ лабораторийн хүрээнд гурван mutant туршсан.

### 5.1. Mutant 1 — Идэвхгүй оюутны шалгалтыг арилгах

Үндсэн код дахь:

```java
if (!student.active()) return "ERROR_INACTIVE_STUDENT";
```

гэсэн нөхцөлийг арилгасан.

Ингэснээр идэвхгүй оюутан бүртгэлийн дараагийн шат руу шилжих боломжтой болсон.

**Үр дүн:** A3 тест хүлээгдэж байсан `ERROR_INACTIVE_STUDENT` утгын оронд өөр үр дүн авсан тул амжилтгүй болсон.

Энэ нь тест идэвхгүй оюутны шалгалт алга болсон гэдгийг илрүүлж чадсаныг харуулна.

### 5.2. Mutant 2 — Бүртгэл хадгалах үйлдлийг арилгах

Үндсэн код дахь:

```java
repository.saveRegistration(studentId, courseId);
```

гэсэн method дуудалтыг арилгасан.

Ингэснээр service амжилттай үр дүн буцаасан ч бүртгэлийг бодитоор хадгалах үйлдэл хийгдэхгүй болсон.

**Үр дүн:** A1 болон A5 тестүүд `saveRegistration()` method дуудагдаагүй болохыг илрүүлж, амжилтгүй болсон.

Энэ туршилт нь зөвхөн буцаах утгыг шалгахаас гадна системийн шаардлагатай үйлдлүүдийг `verify()` ашиглан шалгах нь чухал гэдгийг харуулсан.

### 5.3. Mutant 3 — Null шалгалтын нөхцөлийг өөрчлөх

Үндсэн код дахь:

```java
if (studentId == null || courseId == null)
```

нөхцөлийг:

```java
if (studentId == null)
```

болгон өөрчилсөн.

Ингэснээр `courseId` null байх тохиолдолд анхны хамгаалалтын шалгалт ажиллахаа больсон.

**Үр дүн:** A6 тест `IllegalArgumentException` шидэгдэх ёстой байсан боловч exception гараагүй тул амжилтгүй болсон.

Энэ туршилт нь null утгатай оролтын аль нэг шалгалтыг санамсаргүй орхиход unit test илрүүлж чаддагийг харуулсан.

### 5.4. Mutation testing-ийн нэгтгэл

| Mutant | Өөрчилсөн хэсэг | Илрүүлсэн тест | Үр дүн |
|---|---|---|---|
| Mutant 1 | Идэвхгүй оюутны шалгалт | A3 | Killed |
| Mutant 2 | Бүртгэл хадгалах үйлдэл | A1, A5 | Killed |
| Mutant 3 | Null шалгалт | A6 | Killed |

**Нийт 3 mutant-ийн 3-ыг нь тестүүд илрүүлсэн.**

Эдгээр туршилтын дэлгэрэнгүй Maven output-уудыг `results/mvn-test-mutant-1.txt`, `results/mvn-test-mutant-2.txt`, `results/mvn-test-mutant-3.txt` файлуудад тус тус хадгалсан.

Mutation testing-ийн үед `BUILD FAILURE` гарсан нь тухайн туршилтын зорилготой нийцэж байгаа юм. Учир нь зориудаар өөрчилсөн кодын алдааг тестүүд илрүүлж, хүлээгдэж буй шалгалтууд амжилтгүй болсон гэсэн үг. Туршилт бүрийн дараа үндсэн `CourseRegistrationService.java` кодыг анхны хувилбарт нь сэргээж, эцэст нь `mvn clean test` ажиллуулан бүх тест дахин амжилттай болсон эсэхийг баталгаажуулсан.

## 6. Mockito-ийн ашигласан боломжууд

Лабораторийн ажлын хүрээнд дараах Mockito боломжуудыг ашигласан.

| Mockito боломж | Зориулалт |
|---|---|
| `@Mock` | Хамаарлыг mock объект болгон үүсгэх |
| `@InjectMocks` | Mock хамаарлыг service объектод дамжуулах |
| `when()` | Mock method-ийн хариу үйлдлийг тохируулах |
| `thenReturn()` | Mock method-оос буцаах утгыг тодорхойлох |
| `thenThrow()` | Exception гарах нөхцөлийг дуурайлгах |
| `verify()` | Method дуудагдсан эсэхийг шалгах |
| `never()` | Method огт дуудагдаагүй эсэхийг шалгах |
| `ArgumentCaptor` | Method-д дамжуулсан аргументыг барьж авах |
| `lenient()` | Тодорхой нөхцөлд ашиглагдаагүй stub-ийн шалгалтыг зөөлрүүлэх |

Эдгээр боломжийг ашигласнаар service-ийн буцаах утга, exception боловсруулах байдал, repository болон email sender-тэй харилцах үйлдлүүдийг тус тусад нь шалгах боломжтой болсон.

## 7. AI ашиглалт

Энэхүү лабораторийн ажлын явцад AI хэрэгслийг туслах зорилгоор ашигласан.

AI-ийн тусламжтайгаар Mockito болон JUnit 5-ийн annotation, mock тохиргоо, verification, parameterized test болон mutation testing-ийн ойлголтуудыг нягталж, тестийн бүтэц болон тайлангийн найруулгыг сайжруулахад дэмжлэг авсан.

Гэхдээ тестийн үр дүн, Maven build-ийн төлөв, mutation testing-ийн алдаа болон амжилтын мэдээллийг төслийн орчинд команд ажиллуулж шалган, гарсан output-уудыг `results/` хавтсанд хадгалсан.

AI-ийн өгсөн тайлбар, санал болгосон кодыг шууд эцсийн үр дүн гэж үзээгүй бөгөөд төслийн бодит хэрэгжилт болон тестийн үр дүнтэй нийцэж байгаа эсэхийг шалгасан.

## 8. Дүгнэлт

Энэхүү лабораторийн ажлаар Mockito ашиглан Java application-ийн unit test боловсруулах үндсэн арга барилыг практикт хэрэгжүүллээ. `CourseRegistrationService` классыг сонгон авч, түүний `StudentRepository` болон `EmailSender` хамаарлуудыг mock object-оор орлуулснаар тухайн service-ийн бизнес логикийг бусад бүрэлдэхүүн хэсгээс тусгаарлан шалгах боломжтой болсон.

A1–A7 тестүүдээр амжилттай бүртгэл, оюутан олдохгүй байх, идэвхгүй оюутан, prerequisite хангагдаагүй байх, имэйл илгээх үеийн exception, null оролт болон имэйлийн агуулга зэрэг ялгаатай нөхцөлүүдийг шалгасан. Харин A8 тестээр parameterized testing ашиглан ижил төрлийн алдаатай нөхцөлүүдийг нэг тестийн бүтэц дотор шалгаж, тестийн кодын давхардлыг багасгах боломжтойг харуулсан.

Энэ лабораторийн хамгийн чухал хэсгүүдийн нэг нь mutation testing байлаа. Үндсэн кодод зориудаар гурван өөр өөрчлөлт оруулахад холбогдох тестүүд тухайн алдааг илрүүлж, гурван mutant бүгд амжилтгүй болсон. Ялангуяа `verify()` ашиглан method-ийн дуудалтыг шалгах, `never()` ашиглан хүсээгүй үйлдлийг хориглох, `ArgumentCaptor` ашиглан дамжуулсан өгөгдлийг баталгаажуулах нь зөвхөн method-ийн буцаах утгыг шалгахаас илүү өргөн хүрээний тест хийхэд чухал болохыг туршилтаар харуулсан.

Мөн тест амжилттай ажиллаж байгаа эсэх болон тест тухайн кодын алдааг илрүүлж чадаж байгаа эсэх нь хоёр өөр ойлголт гэдгийг ойлгосон. Ердийн unit test нь хүлээгдэж буй нөхцөлд код зөв ажиллаж байгааг шалгадаг бол mutation testing нь кодод алдаа оруулахад тестүүд түүнийг илрүүлж чадаж байгаа эсэхийг шалгадаг. Иймээс хоёр аргыг хамтад нь ашиглах нь тестийн найдвартай байдлыг илүү бодитой үнэлэхэд тусалдаг.

Эцсийн `mvn clean test` ажиллуулалтаар нийт 10 тест бүгд амжилттай болж, ямар нэгэн failure, error болон skipped test гараагүй. Мөн гурван mutant бүгд илэрсэн тул боловсруулсан тестүүд зөвхөн энгийн амжилттай тохиолдлыг шалгаад зогсохгүй, тодорхой төрлийн логикийн алдааг илрүүлэх чадвартай болох нь батлагдсан.

**Дүгнэж хэлэхэд**, лабораторийн ажлын үр дүнд Mockito-ийн mock object, stubbing, verification, argument capturing болон JUnit 5-ийн parameterized testing-ийг бодит service дээр хэрэгжүүлж сурсан. Цаашид software testing хийхдээ зөвхөн кодын зөв үр дүнг шалгахаас гадна хамаарлуудтай хэрхэн харилцаж байгааг, хүсээгүй үйлдэл гарахгүй байгааг болон тестүүд зориудаар оруулсан алдааг илрүүлж чадаж байгаа эсэхийг давхар шалгах шаардлагатайг ойлголоо.
